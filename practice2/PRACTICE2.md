# Практика 2. Реализация MVP с использованием ИИ

## Цель работы (по методичке)

1. Реализовать рабочий MVP на микросервисной архитектуре (минимум 2 сервиса).
2. Добавить внешние хранилища и взаимодействие сервисов.
3. Подготовить автотесты (не менее 3 сценариев).
4. Запускать систему локально через `docker-compose`.
5. Задокументировать использование ИИ-инструментов.

## Реализованная функциональность

### Backend
- `gateway` (`practice2/services/gateway`)  
  Единая точка входа. Проксирует:
  - `GET /api/rooms`
  - `POST /api/bookings`
- `booking_service` (`practice2/services/booking_service`)  
  Бизнес-логика:
  - выдача списка переговорок;
  - создание бронирования;
  - проверка конфликтов временных интервалов;
  - валидация `start_time < end_time` и времени в будущем.

### Frontend (React, dark theme)
- `practice2/frontend`  
  Современный UI/UX:
  - темная тема;
  - форма создания брони;
  - список переговорок;
  - отображение последних созданных броней;
  - сообщения об ошибках и успешных операциях.

### Данные и инфраструктура
- PostgreSQL - хранение комнат и бронирований.
- Redis - внешнее хранилище для расширения кэша/lock-механик.
- Docker Compose - локальный запуск всего стека.

## Использованные ИИ-инструменты

- Cursor Agent (генерация шаблонов микросервисов и тестов).
- LLM-ассистент для доработки архитектурных и документационных частей.

## Наиболее полезные промпты

1. "Создай API Gateway на FastAPI для проксирования запросов бронирования в отдельный сервис."
2. "Добавь в booking-service проверку пересечения интервалов и возвращай 409 при конфликте."
3. "Сгенерируй pytest-сценарии для успешного бронирования и конфликтного слота."
4. "Сделай React frontend в темной теме для операций `/api/rooms` и `/api/bookings`."

## Ход работы

### Шаг 1. Инициализация микросервисов
- Созданы `gateway` и `booking_service`.
- Определены контрактные эндпоинты между сервисами.

### Шаг 2. Доработка бизнес-логики
- Добавлены модели `Room` и `Booking`.
- Добавлена проверка пересечений по SQL-условию.
- Добавлены метрики `/metrics` для дальнейшего мониторинга.

### Шаг 3. Реализация frontend
- Создан React SPA (`Vite`).
- Добавлена форма бронирования и клиентские состояния загрузки/ошибок/успеха.
- Добавлена контейнеризация frontend (`frontend/Dockerfile`, `frontend/nginx.conf`).

### Шаг 4. Тестирование
- Тесты backend:
  - `test_list_rooms_returns_seeded_rooms`
  - `test_create_booking_success`
  - `test_create_booking_conflict`

  - `test_gateway_proxy_endpoints`

## Запуск (docker compose)

```bash
cd practice2
docker compose up -d --build
```

После старта доступны:
- Frontend: `http://localhost:3000`
- API Gateway: `http://localhost:8000`

Остановка:

```bash
cd practice2
docker compose down
```

## Локальный запуск frontend в dev-режиме

```bash
cd practice2/frontend
npm install
npm run dev
```

Dev frontend будет доступен на `http://localhost:5173` (с прокси на API).

## Запуск автотестов

```bash
pip install -r practice2/requirements-test.txt
pytest practice2/tests -q
```

## Оценка вклада ИИ

- Сгенерировано ИИ: ~70%
- Доработано вручную: ~30%

## Ошибки и как исправлены

- ИИ не всегда учитывал готовность БД при старте контейнеров: исправлялось перезапуском сервиса после инициализации БД.
- ИИ предлагал неполную валидацию по времени: добавлены проверки в backend.
- Первичная версия frontend-шаблона была не доменная: полностью заменена на UI бронирования.
